# QTTabBar-Next 架构问题修复执行方案

## 总览

针对前期分析识别的三个架构问题（多入口初始化、多真源状态管理、上帝模块），按"先建安全网 → 修核心bug → 优化性能一致性 → 可选结构优化"的策略分 4 个批次推进。每批次遵循 TDD（RED→GREEN→REFACTOR），完成后全量测试 + MSBuild 构建 + git 提交 + 三维 Ultra Review 才能推进下一批。

### 关键发现（三视角调查确认）

- **TabsLocked 实际有 10 个直接写入点**（非前期分析的 5 个），分布在 6 个文件中，全部绕过 `StaticReg.LockedTabsToRestoreList` 内存缓存
- `QTUtility2.WriteRegBinary` 对 `"TabsLocked"` 做特殊双写：同时写 binary `"TabsLocked"` 和 string `"TabsLocked2"`，而 `TabManager.cs:961` 读取的是 `"TabsLocked2"` —— 两条并行持久化路径
- `lstTabBar` 静态字段在构造函数赋值 `this` 但 Dispose/CloseDW 从不清理，`CreateTab` fallback 路径可能触发 `ObjectDisposedException`
- `TabInstanceRegistry.PeekMainInstance()` 已提供等价功能且在 `UnregisterTabBar()` 中正确移除 —— 可直接替换 `lstTabBar`
- InstanceManager/PluginManager 的 Initialize 无幂等守卫，编排器异常后重试会泄漏 WCF ServiceHost 和重复加载插件程序集

## 批次 1：幂等守卫 + 隐式入口收敛（P1 安全网）

**目标**：为非幂等初始化添加守卫，为隐式入口添加显式调用，建立安全网后再修核心 bug。

2. `Initialize` 方法入口添加 `if (_initialized) return;` 守卫

6. `SafeReinitialize()` 中先清理旧资源再重置 `_initialized = false`，然后调 `Initialize()`
7. `GetChannel()` 中 `commClient.State == Opened` 时直接返回，不触发 Initialize

## 风险与缓解

| 风险 | 等级 | 缓解 |
|------|------|------|
| TabsLocked 收敛后 WriteRegBinary 特殊处理移除影响 TabsLocked2 兼容 | 中 | façade 内部仍调 WriteRegBinary 保持双写；TabsLocked2 读取点（TabManager.cs:961）在步骤 2.3 中改为从 RegBackedList 读取 |
| InstanceManager 守卫阻断 SafeReinitialize 恢复 | 高 | SafeReinitialize 先清理旧资源 + 重置 _initialized = false 再 Initialize；加日志记录 |
| RegBackedList.Assign 线程安全性 | 中 | 加 lock 保护 Clear+AddRange 操作；RegBackedList 已有 updating 标志防递归 |
| GBK 编码文件编辑风险 | 高 | 使用 Write 工具字节级处理；QTTabBarClass.cs 等含中文文件可能 GBK 无 BOM |
| syncRoot 锁拆分引入死锁 | 中 | 遵循已有"先释放 syncRoot 再获取 imageListLock"模式；并发测试验证无死锁 |
| 嵌套类独立化需放宽大量 private 成员 | 高 | 按已有范式：特征化测试先行，每步验证语义等价；此批次为可选 |

## 被拒绝的替代方案

1. **直接删除 TabsLocked2 双写逻辑**：被拒绝——需先收敛所有读取点到 RegBackedList，确认无依赖后再移除，避免兼容性中断。保留双写一个版本周期。
2. **将 lstTabBar 改为 WeakReference**：被拒绝——`TabInstanceRegistry.PeekMainInstance()` 已提供等价功能且在 UnregisterTabBar 中正确移除，直接替换更简洁。
3. **批次 1-3 全部并行**：被拒绝——批次 2 修改 QTTabBarClass.cs 大量行，批次 1 的守卫逻辑影响批次 2 的 façade 调用时机，串行更安全。
4. **一次性完成嵌套类独立化**：被拒绝——风险过高，需放宽大量 private 成员，应在前期批次稳定后作为可选批次评估推进。
5. **IPC BinaryFormatter 迁移**：被拒绝（本轮）——虽然 InstanceManager 中仍有 DelToByte/ByteToDel 使用 BinaryFormatter，但已有 SameUserAuthorizationManager 缓解 RCE 风险，且迁移工作量大，不在本轮架构修复范围内。
